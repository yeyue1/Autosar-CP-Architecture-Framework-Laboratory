# 教学标签不等于规范

<!-- doc: boundary-teaching-tags -->
<!-- tags: 教学标签, 42 步, 仿真, 边界 -->
<!-- summary: 说明 STARTUP/RUN 标签、42 步、模块就绪与动画成功都只是教学抽象，而非规范或硬件证据。 -->
<!-- refs: src-model -->

教学界面上的标签、步数与动画都是教学抽象。这篇文档逐条说明它们为什么不能当作规范状态，也不能当作硬件证据。

## 教学标签不是规范状态

<!-- keywords: 教学标签, STARTUP, RUN, Flexible, 规范 -->

教学界面里的 STARTUP I、STARTUP II、RUN 是方便学习的阶段标签，不是 AUTOSAR 规范规定的固定状态集合。把教学标签当成规范术语，会误以为现代 Flexible EcuM 必须实现这些状态。理解标签只是教学抽象，才能正确阅读真实规范中的状态与接口。

## 42 步不是规范要求

<!-- keywords: 42 步, 教学粒度, 启动, 多核, 依赖 -->

7 阶段、42 步是本实验室的教学粒度，不是 AUTOSAR 规定的固定数量。真实工程的启动可能涉及多核、多分区、分阶段初始化与更多配置依赖，步数完全不同。把 42 步记住当成学完了启动，会忽略真正重要的依赖关系与前提条件。

## 模块就绪不等于调用过 Init

<!-- keywords: 模块就绪, Init, DIO, Port, MemIf -->

界面上某模块显示就绪，可能只表示它的下层依赖已准备好，并不意味着一定调用过它的初始化函数。例如 DIO 的硬件准备由 Port 驱动完成，MemIf 没有标准初始化 API。凭模块名机械地拼一个初始化调用，是常见的错误推断。判断是否初始化过，要看实际调用与配置，而不是看界面颜色。

## 动画成功不是硬件可启动

<!-- keywords: 动画, 仿真, 硬件, 集成, 验证 -->

教学动画成功只证明教学模型内部一致，真实 ECU 可启动还需要生成配置、集成模块、目标硬件与实测验证。把动画当成真实 ECU 能跑的证据，是对仿真能力的过度解读。仿真适合在此之前理解依赖与调试思路，而不是替代集成与验证。

## 明确声明非量产

<!-- keywords: 教学级行为仿真, ARXML, CAN, 功能安全, 示例 -->

本实验室明确声明自己是教学级行为仿真：不执行真实 ECU 固件、不生成 ARXML、不连接物理 CAN、不做功能安全认证，DID、DTC、Seed/Key 与时间参数都是示例。保持这种诚实边界，才能让学习者把注意力放在依赖关系与调试方法上，而不被看起来像真的所误导。

# 请求受理不等于完成

<!-- doc: boundary-request-done -->
<!-- tags: 异步, NvM, ComM, 发送确认 -->
<!-- summary: 集中澄清「请求受理」「数据可用」「实际模式」「端到端送达」这些常被混同的边界。 -->
<!-- refs: src-ecum -->

本篇集中澄清一组最容易被混同的边界：请求受理、数据可用、实际模式与端到端送达。每一条都在说明「返回了」与「完成了」之间的距离。

## 请求受理不等于完成

<!-- keywords: 异步, NvM_ReadAll, CanSM_RequestComMode, NvM_WriteBlock, 受理 -->

很多 AUTOSAR 接口是异步的：调用返回只表示请求被受理，真正的完成要靠后续周期处理与通知。NvM_ReadAll 返回 void、CanSM_RequestComMode 返回 E_OK 仅表示接受请求、NvM_WriteBlock 只是入队，都是典型例子。把函数返回当成事情做完，是启动与存储调试中最常见的错误。

## NvM 请求不等于已写入

<!-- keywords: NvM, 队列, 提交, 掉电, 持久化 -->

写 NvM 时，请求只是进入队列，还要经过 MemIf、Fee、Fls、校验与提交才真正持久化。排队期间断电会丢失未提交的写入。因此 NvM 请求已受理与值已写入并掉电保持之间有明确边界。判断是否写入成功，要看提交完成的证据，而不是看请求返回。

## ComM 请求不等于实际模式

<!-- keywords: ComM, 请求模式, 实际模式, CanSM, 许可 -->

ComM 的请求模式表达需求，实际模式由 CanSM 推进控制器与收发器状态后反馈。请求 FULL 与实际处于 FULL 可以暂时不同。只看模块是否变绿判断通信可用，会漏掉权限未放开、模式未确认、应用 PDU 未启用等前提。区分请求、许可与实际模式，是通信调试的基本功。

## 已初始化不等于可调度

<!-- keywords: 初始化, Rte_Start, Rte_StartTiming, BswM_Init, 调度 -->

模块完成初始化，不等于它已经被调度执行、也不等于业务已允许上线。Rte_Start 让 RTE 就绪，Rte_StartTiming 才放开周期；BswM_Init 装载规则，后续求值才逐步放行动作。把已初始化当成已运行，会误判系统在某个时刻到底能不能处理业务。

## 数据可用不等于恢复成功

<!-- keywords: 数据可用, ROM 默认值, 冗余, 恢复, 故障 -->

观察到某块数据可用时，要能区分它是从介质恢复的原值、从冗余副本恢复、还是回退到 ROM 默认值。后两者虽然让数据可用，却意味着原数据可能已损坏或缺失。把数据可用笼统当成恢复成功，会在故障排查中掩盖真实问题。

## 发送确认不等于端到端送达

<!-- keywords: 发送确认, 端到端, E2E, 监督, 送达 -->

底层的发送确认通常表示帧已进入发送过程，不等于远端 ECU 收到或应用已处理。真正的端到端可信要用应用握手、周期监督或 E2E 保护判断。把发送确认当成送达，会掩盖网络丢失、对端未处理等实际问题。

# 常见误解逐条澄清

<!-- doc: boundary-misconceptions -->
<!-- tags: 误解, Flexible, CAN FD, ISO-TP -->
<!-- summary: 逐条澄清把 Flexible 当 Fixed、以为 CAN FD 提升 UDS、以为流控是应用层等常见混淆。 -->
<!-- refs: src-model -->

这一篇把讨论 AUTOSAR 时最常见的几处混淆逐条澄清，从把 Flexible 当 Fixed，到以为 RUN 就等于每条网络都是 FULL。

## 把 Flexible 当 Fixed

<!-- keywords: Flexible, Fixed, BswM, STARTUP, callout -->

把现代 Flexible EcuM 当成旧 Fixed 状态机，是常见误解：Flexible 只保留启动骨架，后续由 BswM 按配置推进，并不存在 Fixed 那套写死的 STARTUP 与 RUN 状态以及 InitTwo 与 InitThree callout。混淆两者会导致对启动顺序、NvM 与 RTE 先后关系的错误预期。

## 以为 CAN FD 提升 UDS 语义

<!-- keywords: CAN FD, UDS, ISO-TP, 流控, 帧数 -->

CAN FD 只扩展单帧载荷与数据段码率，不会改变 UDS 服务语义，也不会消除 ISO-TP 的流控、顺序与超时。以为换成 CAN FD 就能省掉流控或让诊断更高级，是对协议分层的误解。它减少的是帧数，不是协议规则。

## 以为 ISO-TP 流控是应用层

<!-- keywords: ISO-TP, 流控, 应用层, UDS, 负响应 -->

ISO-TP 的流控帧、块大小与 STmin 属于传输层机制，不是应用层语义。把它们当成 UDS 服务的一部分，会混淆协议传输失败与应用层负响应。无响应往往来自传输层，而 7F 开头的负响应才是应用层确实回应。

## 以为 NvM 读失败必须停机

<!-- keywords: NvM, 默认值, 降级, 策略, 恢复 -->

NvM 恢复失败后是否停机、是否用默认值、是否有降级运行，属于项目策略而非规范强制。把读失败必须永久停机或必须无条件用默认值当成通用规则，都忽略了数据重要性差异与降级约束。正确做法是明确每块数据的失败策略。

## 以为 ComM 请求即上线

<!-- keywords: ComM, 请求, 上线, CanSM, 远端 -->

发起 ComM 通信请求不等于总线已进入该模式，也不等于远端 ECU 已上线。请求只是本 ECU 的需求表达，实际模式要靠 CanSM 推进与指示反馈，远端可用性要靠网络证据判断。把本地请求当成全局上线，会误判多 ECU 系统的可用性。

## 以为 RUN 就每条网络都 FULL

<!-- keywords: RUN, FULL, ComM, 通道, 网络 -->

ECU 处于 RUN 并不代表它的每条 ComM 通道都是 FULL：不同网络有不同需求与许可状态，应用可运行与具体网络的实际模式要分开看。用一条通道的状态推断整体业务可用性，是整车级诊断中的常见错判。

# 功能安全与 AUTOSAR 的边界

<!-- doc: boundary-safety -->
<!-- tags: ISO 26262, ASIL, 功能安全, 边界 -->
<!-- summary: 澄清 ISO 26262 与 AUTOSAR 的分工、机制不等于认证、ASIL 与架构以及教学模型的诚实边界。 -->
<!-- refs: src-cdd -->

功能安全常被简化成「用了安全机制」。这篇文档说明 ISO 26262 与 AUTOSAR 的分工、机制与认证的差别，以及教学模型的诚实边界。

## 功能安全与 AUTOSAR 的分工

<!-- keywords: ISO 26262, AUTOSAR, E2E, WdgM, 安全目标 -->

ISO 26262 定义功能安全的目标、流程与安全生命周期，AUTOSAR 提供实现这些目标可用的软件架构与机制，如 E2E、WdgM、内存保护、安全模式。AUTOSAR 本身不是一个安全认证，它是工具与框架；安全目标能否达成，取决于系统设计与验证，而不只是用了某个协议栈。

## 机制不等于认证

<!-- keywords: 功能安全, 认证, E2E, WdgM, 危害分析 -->

采用了 E2E、WdgM、时间保护等机制，不等于通过功能安全认证。认证需要危害分析、安全目标、机制有效性与覆盖度的论证、验证确认与独立评估。把用了安全机制当成已经安全，是常见的过度自信，也可能掩盖机制配置不当带来的新风险。

## ASIL 与软件架构

<!-- keywords: ASIL, 安全需求, 分区, OS-Application, 冗余 -->

ASIL（Automotive Safety Integrity Level）决定安全需求的严格度，进而影响架构选择：是否需要内存分区、独立监督、冗余、时序保护等。AUTOSAR 的分区、OS-Application、内存保护与多核隔离为实现这些要求提供了基础，但如何组合仍由安全分析决定，而不是协议栈自动给出。

## 教学模型的诚实边界

<!-- keywords: 教学, 功能安全, 看门狗, 信任链, 边界 -->

本实验室明确不做功能安全认证：没有真实 OS、硬件寄存器、看门狗硬件与安全启动信任链，DID、DTC、Seed/Key 与时间参数都是示例。因此它可以帮助理解机制概念与依赖关系，但不能作为任何安全论证的证据。理解这条边界，是使用教学仿真时最重要的自律。

## AUTOSAR 不是安全需求的来源

<!-- keywords: AUTOSAR, 安全需求, 危害分析, 安全目标, 机制 -->

AUTOSAR 提供机制，但安全需求来自车辆功能与危害分析，而不是协议栈。先有安全目标与安全需求，再选择 AUTOSAR 机制去满足它；反过来因为有 AUTOSAR 所以安全是错误因果。区分来源与手段，才能把架构设计与安全论证放在正确的位置。
