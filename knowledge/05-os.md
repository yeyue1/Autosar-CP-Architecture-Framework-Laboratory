# 固定优先级抢占与调度表

<!-- doc: os-scheduling -->
<!-- tags: OS, 固定优先级, 抢占, 调度表 -->
<!-- summary: 讲清固定优先级抢占、调度表同步、基本/扩展任务差异、激活终止与栈负载问题。 -->
<!-- refs: src-os -->

这篇文档讲 OS 调度语义的基础：固定优先级抢占、调度表、基本任务与扩展任务的差别，以及栈与优先级反转带来的现实约束。

## 固定优先级抢占

<!-- keywords: 固定优先级, 抢占, 任务, 优先级, 就绪 -->

AUTOSAR OS 采用固定优先级抢占式调度：每个任务有静态优先级，更高优先级任务一旦就绪就抢占当前运行的低优先级任务。任务状态包括 running、ready、waiting、suspended 等。固定优先级保证行为可分析，但也意味着高优先级任务过密会饿死低优先级任务，因此优先级分配与 CPU 负载评估很重要。

## 调度表的作用

<!-- keywords: 调度表, Schedule Table, 同步计数器, 抢占, 同步点 -->

调度表 Schedule Table 按时间自动激活绑定在表上的任务或设置事件，由同步计数器推进，可在指定同步点对齐。它适合有严格时间序列的周期性处理，与固定优先级抢占并行工作：调度表决定何时到期，抢占规则决定谁现在能跑。两者结合能表达复杂时序，但也增加了同步与抖动的分析难度。

## 基本任务与扩展任务

<!-- keywords: 基本任务, 扩展任务, SetEvent, waiting, 事件 -->

基本任务 Basic Task 只能在运行与挂起之间切换，不能等待事件；扩展任务 Extended Task 可以等待事件，进入 waiting 状态，被 SetEvent 唤醒后回到 ready。周期处理常用基本任务，需要等待外部事件的处理常用扩展任务。选错任务类型会导致无法表达等待语义，或引入不必要的阻塞。

## 任务的激活与终止

<!-- keywords: 激活, TerminateTask, 调度表, 可调度性, 阻塞 -->

任务的激活方式包括自动启动、被其它任务或 ISR 激活、以及由调度表激活。任务结束时调用 TerminateTask 让出处理器，若任务卡在忙等则会破坏可调度性分析。AUTOSAR OS 要求任务有明确的终止点或阻塞点，以便调度器接管；无限循环且不让出的任务会拖垮整个系统的时间行为。

## 栈与优先级反转

<!-- keywords: 栈, 栈溢出, 优先级反转, 资源, 负载 -->

每个任务与 ISR 需要独立的栈空间，栈大小与最大调用深度、局部变量量相关，配置过小会导致栈溢出。负载方面，固定优先级调度的经典问题是优先级反转，共享资源会让高优先级被低优先级间接阻塞，需要用资源协议或优先级提升缓解。栈与负载分析是量产工程里必不可少的一步。

# Cat1/Cat2 中断、资源与事件

<!-- doc: os-isr -->
<!-- tags: OS, ISR, Cat1, Cat2, 资源 -->
<!-- summary: 区分 Cat1/Cat2 ISR、说明 ISR 返回调度、资源临界区与 ISR 任务职责分工。 -->
<!-- refs: src-os -->

中断是实时系统里最容易写错的一层。这篇文档区分 Cat1 与 Cat2、说明 ISR 返回时的调度决策，以及资源、屏蔽窗口与职责分工。

## Cat1 与 Cat2 中断

<!-- keywords: Cat1, Cat2, ISR, SetEvent, 中断 -->

AUTOSAR OS 区分两类中断：Category 1（Cat1）ISR 不经过 OS、不调用 OS 服务，开销最小，常用于极短且时间关键的硬件事件；Category 2（Cat2）ISR 由 OS 管理，可以调用部分 OS 服务，如激活任务、SetEvent，返回时触发调度决策。把 Cat1 当成可以随意调 OS 服务，会导致未定义行为。

## ISR 返回与调度

<!-- keywords: Cat2, ISR, SetEvent, 调度, 抢占 -->

Cat2 ISR 执行完毕返回时，OS 会检查是否有更高优先级任务因此就绪，如有则发生抢占。这就是为什么 ISR 里 SetEvent 能唤醒扩展任务：事件把任务置为 ready，返回路径再做调度。理解这条中断、事件、任务的链，才能解释一次硬件中断如何最终变成某个任务被执行。

## 资源与临界区

<!-- keywords: GetResource, ReleaseResource, 临界区, 资源协议, 竞争 -->

当任务或 ISR 需要访问共享数据时，用 GetResource 与 ReleaseResource 声明临界区，OS 在执行临界区期间按配置提升到资源上限优先级或关中断，避免竞争。资源协议能防止并发访问破坏数据，但滥用会让高优先级任务被长时间阻塞。合理划分临界区粒度是实时系统的常见功课。

## 中断屏蔽与响应性

<!-- keywords: 关中断, 屏蔽, 中断优先级, 响应性, 时序 -->

关中断或长时间屏蔽会延迟 ISR 响应，影响时序确定性。AUTOSAR OS 用中断优先级与屏蔽机制管理嵌套与延迟，但屏蔽窗口应尽量短。把大段处理放进关中断区域，会牺牲系统的响应性，即使逻辑正确也可能违反时序要求。这是实时性设计中需要权衡的典型点。

## ISR 与任务的职责分工

<!-- keywords: ISR, 事件, 任务, 中断延迟, 职责 -->

常见做法是让 ISR 只做最少的事，例如读取硬件、清标志、发事件，把较重逻辑放到被唤醒的任务里执行。这样既缩短中断处理时间，又让复杂处理可在允许调用更多服务的任务上下文中进行。把重逻辑直接塞进 ISR，不仅拉长中断延迟，还可能因在 Cat1 中误调 OS 服务而出错。

# 时间保护机制

<!-- doc: os-timing-protection -->
<!-- tags: OS, 时间保护, WCET, 执行预算 -->
<!-- summary: 讲清时间保护的执行预算与到达间隔监督、与 WCET 和 WdgM 的关系及启用代价。 -->
<!-- refs: src-os -->

时间保护把时序正确性从设计约束变成运行时可检测的机制。这篇文档讲执行预算与到达间隔监督，并说明它与 WCET、WdgM 各自的分工。

## 时间保护是什么

<!-- keywords: 时间保护, 执行预算, 到达间隔, 错误钩子, 任务 -->

时间保护 Timing Protection 监控任务与 ISR 的执行时间预算和到达间隔，防止某个实体超时运行或过快重复激活而拖垮系统。它为每个受保护对象配置执行预算与最小、最大到达间隔，一旦越界，OS 依配置触发保护动作，例如调用错误钩子或终止任务。它把时序正确性从设计约束变成运行时可检测的机制。

## 执行预算与 WCET

<!-- keywords: 执行预算, WCET, 时间保护, 可调度性, 超时 -->

执行预算通常约等于或略高于 WCET（最坏情况执行时间）。预算设得过大失去保护意义，设得过小则误报。因此时间保护依赖可信的 WCET 分析。它不能替代 WCET 分析，而是把分析结果固化成运行时守卫；两者配合，才能既保证可调度性又能捕捉异常的超时行为。

## 到达间隔的监督

<!-- keywords: 到达间隔, 激活, 中断风暴, 时间保护, 时序 -->

到达间隔监督关注激活频率：若某任务在最小间隔内被重复激活，可能意味着中断风暴或逻辑错误；若超过最大间隔未到达，可能意味着上游缺失。时间保护把这两种偏差都变成可检测事件，帮助定位那些不表现为崩溃、却破坏时序的隐性问题。

## 与 WdgM 的差别

<!-- keywords: 时间保护, WdgM, 看门狗, alive, 监督 -->

时间保护关注任务与 ISR 级的执行和到达预算，属于 OS 机制；WdgM（Watchdog Manager）关注的是功能级存活：检查受监督实体是否按时报告 alive，并在失败时触发看门狗复位或降级。二者都关乎时序，但层次不同，前者防单实体失控，后者防整体功能停滞，工程上常配合使用。

## 启用时间保护的代价

<!-- keywords: 时间保护, 配置, 开销, 保护动作, 鲁棒性 -->

启用时间保护需要配置每个受保护对象并承担少量运行时开销与测量误差，还要处理保护动作带来的系统行为，例如任务被终止后如何恢复。它不是免费的开关，需要在诊断能力、系统鲁棒性与额外复杂度之间权衡。教学实验只讲语义，不实现真实 OS 的保护域与硬件计时，不能据此当作量产配置。

# OS-Application、IOC 与 Spinlock

<!-- doc: os-multicore -->
<!-- tags: OS, OS-Application, IOC, Spinlock -->
<!-- summary: 说明 OS-Application 边界、跨核 IOC 通信、Spinlock 用途、核归属与共享初始化顺序。 -->
<!-- refs: src-os -->

多核不是把单核代码复制几份。这篇文档说明 OS-Application 的边界、跨核 IOC 通信、Spinlock 的适用范围与核归属和初始化顺序。

## OS-Application 的边界

<!-- keywords: OS-Application, 任务, ISR, 保护, 核 -->

AUTOSAR OS 用 OS-Application 划分软件单元，每个 OS-Application 可以有自己的任务、ISR、报警与资源，并可运行在不同核上。OS-Application 是信任与保护的基本单位：跨 OS-Application 的访问需要受控接口，某些服务仅允许在特定类型的 OS-Application 内调用。它把谁拥有什么显式化。

## IOC 的跨核通信

<!-- keywords: IOC, OS-Application, 跨核, 队列, 同步 -->

IOC（Inter-OS-Application Communicator）用于在同一核或不同核的 OS-Application 之间传递数据，消息通过队列或缓冲投递，由发送与接收侧的调用配合完成。它替代了跨核直接共享变量的不安全做法，让数据传递有明确的同步点与边界。理解 IOC，才能解释跨核数据为什么要在接收端任务运行时才被处理。

## Spinlock 的用途

<!-- keywords: Spinlock, 多核, 临界区, 自旋, 优先级反转 -->

Spinlock 用于多核间保护短小的共享临界区：一个核获取锁后，其它核自旋等待直到释放。它适合极短的临界区，因为自旋会消耗 CPU；临界区过长会浪费算力并增加优先级反转风险。Spinlock 与单核资源协议解决的是不同范围的问题，多核共享资源必须用能跨核同步的机制。

## 核归属与启动

<!-- keywords: 多核, StartCore, StartOS, 核归属, 运行数据 -->

多核 OS 共享配置与大量代码，但每个核有自己的运行数据：任务表、栈、中断向量与调度状态。主核负责共享初始化并调用 StartCore 启动其它核，被启动的核各自调用 StartOS。任务与 ISR 归属于某核，不能随意在另一核运行。搞清核归属，才能避免把单核假设错误地套到多核上。

## 共享资源的初始化顺序

<!-- keywords: 多核, 共享资源, 初始化, 同步, 启动屏障 -->

多核启动时，共享时钟、RAM 与外设在主核早期初始化，其它核在依赖就绪后才被拉起。若某核过早访问未初始化的共享资源，会得到不确定结果。因此核间需要明确的同步与顺序约定，通常由启动屏障保证所有核到达某一就绪点后再统一放行。共享资源的初始化顺序是多核启动正确性的关键。

# 多核启动屏障

<!-- doc: os-startup-barrier -->
<!-- tags: 多核, 启动屏障, 同步, 超时 -->
<!-- summary: 解释启动屏障为何必要、屏障的超时与降级、屏障后的统一放行以及教学伪 API 的边界。 -->
<!-- refs: src-os -->

多个核并行启动时，某些工作必须等所有核都到齐。这篇文档解释启动屏障的必要性、超时降级、屏障之后的统一放行，以及教学伪 API 的边界。

## 启动屏障的必要性

<!-- keywords: 启动屏障, 多核, 就绪点, 同步, 共享资源 -->

多核并行启动时，某些后续工作必须等所有核都到达就绪点才能开始，例如放开依赖通信核的业务、统一启动时间基准。启动屏障就是用一组同步点让各核在此汇合，先到者等待、最后者放行。没有屏障，先完成的核可能提前使用尚未就绪的共享资源或服务。

## 屏障与超时降级

<!-- keywords: 屏障, 超时, 降级, 复位, 启动超时 -->

屏障等待需要超时与失败策略：若某个核启动超时，主核不能无限等待，而应进入已定义好的降级或复位路径。教学故障场景让一个核启动超时，其它核可到局部就绪，但屏障阻止依赖该核的任务被错误放行。这说明屏障不仅是同步点，也是把部分失败转成受控状态的位置。

## 屏障之后的统一放行

<!-- keywords: 屏障, RTE, BSW, 并行, 就绪 -->

越过屏障后，各核才统一推进依赖全局就绪的工作：启动 RTE 事件、放开 BSW 周期处理、对外声明 ECU 就绪。屏障之前的初始化应是局部且可并行的，屏障之后的动作则依赖全局一致。把这两段职责分清，能解释为什么某些初始化可以并行、某些必须串行在屏障之后。

## 教学伪 API 的边界

<!-- keywords: 屏障, AUTOSAR, 缓存一致性, WCET, 多核 -->

教学里用 StartupBarrier_WaitAll 之类的名字表达屏障，但这些是项目级伪 API，不是 AUTOSAR 标准接口。真实多核设计还要处理内存归属、缓存一致性、启动超时、安全机制、锁顺序、WCET 与关机路径，远不是一次等待调用能概括的。理解这一边界，才不会把教学示意当成可直接生成的多核配置。
